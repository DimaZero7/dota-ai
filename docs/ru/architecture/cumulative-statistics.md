# Накопительная статистика: каталог и контракты

[Архитектура](README.md) · [Контракты работающей версии](analysis-levels.md) · [English](../../en/architecture/cumulative-statistics.md)

Статус: **проектирование задачи 4 завершено**. Проведён локальный аудит десяти сохранённых матчей; ниже принят контракт для реализации в задачах 5–10. На момент завершения задачи 4 движок был только спроектирован. Теперь [числовые L1–L4 реализованы в задаче 5](../development/numeric-analysis.md); накопительное хранилище и обновление профиля ещё впереди. Работающий пример задачи 3 по-прежнему использует авторские ответы на L2–L6.

Главный принцип: L0–L4 преимущественно собирают и вычисляют; L5 обобщает числовые данные по условиям, а аналитик связывает закономерности; L6 объясняет игроку стиль, особенности и направления развития. Проза на каждом нижнем уровне не является обязательным промежуточным продуктом. Число должно иметь смысл и проверяемое определение, но само не присваивает игроку характер.

## Результат аудита

[Воспроизводимый аудит](../../../data/prototype/statistics-audit.json) охватывает **137 путей полей**, 10 матчей, исходные ответы OpenDota и STRATZ. Проверяются размеры и SHA-256 исходных файлов, идентичность матча и участников. `states_by_match` сохраняет наличие значения, нуля, false, пустого списка, null и отсутствующего ключа; состояния могут сочетаться внутри одного журнала. `matches_with_numeric_or_value` означает наличие хотя бы одного значения, а не полное покрытие. Аудит полей игрока относится к целевому игроку; отдельные счётчики проверяют наличие координат и экономики у всех десяти участников.

| Наблюдение | Решение для каталога |
| --- | --- |
| STRATZ: журналы перемещений и экономики присутствуют у всех 100 участников десяти матчей | Можно проектировать командные разности и пространственные признаки; полное покрытие времени ещё нужно измерять |
| По 11 итоговым показателям всех 100 участников расхождений OpenDota/STRATZ не найдено | Итоговый KDA, GPM, XPM, урон и др. использовать отдельно от событийных сумм |
| Число записанных смертей совпадает с итогом в 10/10; убийств — в 9/10; ассистов — в 3/10; добиваний — в 9/10 | Пригодность задаётся для конкретного показателя. Расхождение ассистов не исключает матч из статистики опыта или смертей |
| `experienceEvents` есть в 10/10; в матче 8955721990 записано 64 400 XP, а `1185 XPM × 3748 / 60 = 74 023` | Считать **записанный опыт**; не подменять им весь полученный опыт. Причина расхождения пока не установлена; механика предела уровня не предполагается |
| `timeDead`: сумма 551 против OD `life_state_dead=552` в одном разобранном матче; 91 против 90 в другом | Это источник оценки интервалов смерти с погрешностью, а не доказанное точное время отсутствия или цена ошибки |
| OpenDota: события объектов, командные драки, временные ряды XP и жизнь вардов доступны только в 2/10 | Дополнительная проверка и ограниченные признаки; не обязательный источник для всей выборки |
| `stats.wards` и `wardDestruction`: значения в 8/10, пустые списки в 2/10, null нет | Ноль записей допустим; фактическая полезность обзора из этого не следует. Коды типов требуют проверенного соответствия |
| `inventoryEvents`: во всех матчах только стартовая запись на −89 секунде | Нельзя восстановить доступность предмета в конкретный момент. Покупка и применение остаются отдельными наблюдаемыми событиями |
| У координат максимальные промежутки между наблюдениями целевого игрока — 15–105 секунд в зависимости от матча | Нельзя считать плотность записей временем присутствия. Нужны покрытие времени и явно заданная обработка пропусков |
| OD `average_rank` и ST `averageRank` отсутствуют/null в 10/10; ST `rank` заполнен | Хранить ранг STRATZ с происхождением, не выдавать его за подтверждённый индивидуальный ранг на момент игры |
| STRATZ `isStats=false` в двух матчах при имеющихся журналах | Проверять реальные поля; этот флаг не является запретом анализа |

Наличие поля в сохранённой GraphQL-схеме не доказывает, что оно было запрошено или вернулось. Для каталога используются фактические значения исходных ответов. Описания многих полей в сохранённой схеме пусты: смысл спорных флагов, минутных массивов, типов объектов и систем координат должен проходить отдельную проверку до содержательных выводов. Метаданные запросов и схема сохраняются в исходных снимках. Чаты и чужие профили в каталог не включены.

## Каталог и паспорт

[Машиночитаемый каталог](../../contracts/statistics-catalog.json) содержит **46 паспортов: 26 core, 15 additional, 5 candidate**. Он общий для RU/EN; названия показателей двуязычные. `core` — обязательный объём будущего движка, а не обещание полной доступности каждого показателя во всех матчах. `additional` использует уже имеющиеся поля, но может требовать проверки семантики. `candidate` заблокирован недостатком данных или проверенного определения; автоматически подключать источник ради него нельзя.

Полный паспорт складывается из записи показателя и `passport_defaults`: ID и версия метода, определение и формула, единицы, числитель/знаменатель, окно, источник через `audit_fields`, контекст сравнения, уровень, зависимости, ограничения, проверка, покрытие и необходимое состояние для обновления. `depends_on` описывает происхождение вычисления; формальный обмен между уровнями дополнительно переносит необходимые базовые числа через непосредственных детей. Общие правила расчёта:

- Окна полуоткрытые `[a,b)`. Для целочисленного последнего события допускается верхняя граница `duration+1`, но длительность экспозиции остаётся `duration`, без добавления секунды.
- Базовые этапы — десятиминутные интервалы, последний обрезан окончанием матча. Это временные корзины, не автоматически распознанные стратегические фазы. Этап после окончания матча отсутствует; его показатели не равны нулю.
- В снимках экономики требуется значение не старше 5 секунд. Командная разность требует десяти свежих значений. Пропуск разрывает последовательность; его нельзя превращать в скачок преимущества.
- Оценка времени смерти — объединение интервалов `[time,time+timeDead)` с обрезкой по матчу и этапу. Она сохраняет статус приближения, особенно при buyback. Сумма исходного `timeDead` нужна для сверки и хранится отдельно.
- По каждому показателю сохраняются собственные `eligible`, `missing`, `conflicting`, `censored`, `observed_empty`, временное покрытие и причины исключения. Конфликт может сосуществовать с измеренным значением; итоговый `quality_status` определяет допуск к конкретному сравнению. Отсутствующий знаменатель или знаменатель 0 даёт null.
- Среднее индивидуальных долей и отношение суммарных числителей к суммарным знаменателям — разные оценки. Каталог требует сохранять обе основы, явно называя способ агрегации.
- Метод, параметры порогов, часы источника, версия группировки/сетки и ревизия источника входят в происхождение. Пороги 5 секунд, 90/120 секунд, 1000 золота и 20 матчей — настройки прототипа, не установленные законы игры.

## Что создаёт каждый уровень

| Уровень | Новое содержание | Компактный выход вверх | Что остаётся в хранилище |
| --- | --- | --- | --- |
| L0 — источники | Идентичность, доступность, конфликты, происхождение | Манифест источников и качества | Оригинальные ответы, запросы, схемы, SHA |
| L1 — факты | Типизированные события, снимки и полный контекст участников | Числовые записи с временной шкалой, единицами и качеством | Полные журналы и индекс событий |
| L2 — окна/эпизоды | Суммы XP/золота по причинам, интервалы смерти, покупки/действия; условные окна и цензурирование | Числители, знаменатели, длительности, состояния и небольшой набор ключей раскрытия | Состав событий каждого окна; исключительные аннотации |
| L3 — этапы | Темпы, доли времени, распределения, смена состояния команды, пространственное покрытие | Векторы этапов и статистики распределения с раздельными источниками | Подробные временные ряды и локальные окна |
| L4 — матч | Траектория этапов, доли ресурсов, контекстная строка матча и его место в наблюдаемой последовательности | Ограниченная числовая строка матча; полный пик хранится в контекстном справочнике | Все этапы, интервалы и происхождение |
| L5 — дистанция | Условные распределения, совместные таблицы, тенденции, сессии, контрпримеры и изменения | Группы условий, размеры выборки, эффекты/неопределённость, история проверяемых гипотез | Строки матчей, вклад каждого матча, индексы групп/контрпримеров |
| L6 — профиль | Связь подтверждений и ограничений в портрет, приоритеты и проверяемые эксперименты | Личное объяснение и изменение профиля; ссылки на группы L5 | Версии утверждений и адресные примеры |

L5 сочетает вычисления и анализ: код готовит распределения и условные связи, текущий Codex определяет, что они означают, противоречат ли друг другу и чего не хватает. На L6 он объясняет это игроку. При обычном пополнении L2–L4 не требуют модельного ответа.

Данные, которые не становятся новым показателем на промежуточном уровне, проходят через него в виде компактного числового контекста с происхождением: например, итоговые убийства/ассисты для L4. Полные журналы при этом не переносятся. Ссылка на детей может быть хешем манифеста в хранилище, а не списком тысяч ID в пакете модели.

## Пять сквозных цепочек

| Семейство | L1 → L2 | L3 → L4 | L5 → L6 |
| --- | --- | --- | --- |
| Опыт | События XP/уровней → записанный XP по причинам и времена уровней | Темп XP этапа → траектория развития при данном герое/позиции | Распределения по условиям, изменения темпа → гипотеза о развитии игрока с оговоркой о полноте XP |
| Смерти | Время/`timeDead` → окна смерти и возврат к записанной активности | Доли времени смерти этапов → их расположение в траектории матча | Связь с исходным преимуществом/результатом и её устойчивость → приоритет проверки решений, без автоматического ярлыка ошибки |
| Ресурсы | Экономические снимки/потоки → собственная и командная разность | Темпы и переходы → доля ресурсов и траектория | Условная связь с участием/объектами → гипотеза о способе использования ресурсов, не оценка по одному GPM |
| Пространство | Координаты → дистанции с покрытием времени | Сетка наблюдаемого времени → распределение матча по этапам | Различия по ролям/состоянию → проверяемая гипотеза о перемещениях; смысловые области только после валидации карты |
| Сессии | Время/результат матча → длительности игровых окон | Покрытые этапы → компактная строка, UTC-разрыв, порядковый номер сессии | Изменения показателей между соседними играми и после результата → гипотеза для проверки режима игры, не утверждение об усталости/тильте |

Сессионная связь возникает только после сопоставления завершённых строк матчей на L4. Нельзя приписывать одному событию информацию о будущей игре. Граница сессии в прототипе — более 60 минут между окончанием и следующим началом; обязательна проверка чувствительности при 30/90 минутах. Начало выборки цензурировано, пробелы истории разрывают достоверную последовательность. Список последних рейтинговых игр не доказывает отсутствия других игр между ними.

## Контракт обмена

Планируемый формат `numeric-analysis-1` не заменяет существующие файлы автоматически. Обязательная оболочка:

```text
schema_version, id, revision, level, scope, as_of
context_ref, context_summary, method_versions, parameter_hash
source_manifest_ref, children_manifest_ref
measurements[{metric_id, method_version, value, unit, numerator, denominator,
              coverage, quality_status, uncertainty, provenance_ref}]
interpretations[]
drill_index_ref, omitted{groups, features, examples, reason}
```

`scope`: для L1–L4 — account/match/slot/window; для L5 — account/cohort/window; для L6 — account/profile revision. `value` допускает число, вектор или структурированную запись по паспорту. `coverage` содержит число подходящих матчей/событий и известное время; `uncertainty` — метод, границы/описание и причину отсутствия оценки. Отсутствующий доверительный интервал не означает нулевую неопределённость. До выбора и проверки статистического метода в задаче 7 результат описательный; он не объявляется значимым.

`interpretations=[]` допустимо на L1–L4. На L5–L6 аннотация содержит ID утверждения, тип observation/interpretation/hypothesis, область применимости, поддерживающие/противоречащие группы, альтернативы, ограничения, следующую проверку, версию аналитика и зависимости. У L6 дополнительно 1–3 приоритета: действие, исходное измерение, ожидаемый проверяемый признак изменения, критерий пересмотра.

Пакет L6 содержит выбранные группы L5 и прежние утверждения, не список матчей. Бюджет прототипа: вход до 32 000 UTF-8 байт, резерв ответа 16 000 байт, отдельное адресное раскрытие суммарно до 8 000 байт за 3 вызова. Это ограничение байтов, не обещание точного количества токенов. Код задачи 9 должен измерять сериализованный размер, отражать пропуски и отказывать в скрытом усечении необходимых оснований. Основной отчёт никогда не зависит от незаявленного «я помню остальные игры».

## Группировка и границы выводов

Базовый ключ сравнения: герой, оценённая позиция, режим, этап, известные версии источников/карты; сохраняются наблюдаемая линия, сторона, оба пика, начальная командная разность и происхождение ранга. При анализе этапа используется состояние **до** этапа; конечное состояние нельзя выдавать за предварительно известный фактор. IDs патча OD/ST имеют разные пространства значений; их нельзя сравнивать как одинаковые номера. Мета отключена.

Полные составы сохраняются для раскрытия. При малой точной группе сначала показывается её размер; более широкое сравнение явно перечисляет снятые условия и новый состав. Например: «тот же герой/позиция, разные пики», затем «та же позиция, разные герои» — отдельные результаты. Неизвестная позиция/ранг/сторона не входит в подтверждённую группу. Роли и герои не объединяются в единую оценку игрока без состава выборки.

Прототипное правило: при `n<5` только описание наблюдений; если в любой сравниваемой ячейке исхода `<5` игр, устойчивость связи не заявляется. Это минимальный фильтр, а не достаточное доказательство при `n>=5`. На текущих 9 победах/1 поражении надёжно связать показатель с шансом победы нельзя. Проверяются число проверенных гипотез, зависимость соседних игр, изменение состава групп и временная проверочная выборка. Корреляция конечной статистики с победой не устанавливает причину или пригодность признака для предсказания.

## Обновление без чтения старых матчей

У каждого паспорта перечислен `retention`: необходимые суммы, совместные записи, компактные строки матчей, временные ряды, интервалы, сетки, хронология, исходники или версии утверждений. Это обязательная граница обещания «1000 + 10».

1. Для уже определённых признаков сохраняются числовые строки матчей и их вклад в агрегаты. Новые десять матчей проходят L0–L4, добавляют вклад в затронутые группы L5, создают пакет изменений для L6. Аналитик не читает старые 1000 игр.
2. По одним суммам можно обновить среднее/дисперсию и заранее заданные доли. Точную медиану/IQR, новое разбиение или неизвестную ранее связь нельзя восстановить только из средних. Для них используются компактные строки и совместные данные; чтение таких строк кодом допустимо и не равно чтению исходных событий моделью.
3. Для исправленного/повторно полученного матча выполняется замена вклада по `(account,match,method,source revision)`, не повторное прибавление. Агрегат и журнал вкладов обновляются атомарно. Обнаружение дубля не меняет счётчики.
4. При последовательном добавлении для сессий достаточно сохранённого конца предыдущей игры, результата, длины серии, порядкового номера и подтверждённости границы. Вставка старой игры/исправление времени требует пересчёта затронутой последовательности до следующей достоверной границы; длинная серия может затронуть весь оставшийся хвост компактной хронологии.
5. Изменение формулы, сетки, часов, семантики события или недостающий новый признак требует целевого пересчёта. Если компактных данных недостаточно — читаются нужные старые ряды/исходники кодом. Покрытие старой истории до пересчёта явно неполное. Восстановить потерянную информацию из прежнего профиля нельзя.
6. Любое пополнение обновляет применимые числа или покрытие. Аналитик пересматривает только затронутые утверждения; стабильное описание может сохраниться. В истории фиксируется «оснований изменить текст не появилось», а не искусственное изменение характера после каждой игры.

Верхнему уровню передаются названия условий и агрегаты: «Jakiro, позиция 2, четыре матча, длительность 37:41–62:28». Фраза «против Arc» допустима только внутри раскрытого примера с ID, датой, героем, позицией и ссылкой. Ограничения также обобщаются до уровня группы.

## Когда нужна модель внизу

Исключения: противоречивый числовой сигнал требует просмотра эпизода; пользователь просит конкретный момент; проверяется новая гипотеза и её контрпример. Модель получает ограниченное окно, наблюдаемые условия и точный вопрос. Она не должна проходить все эпизоды «на всякий случай».

Аннотация кешируется по хешам исходных фактов, метода, окна, вопроса, правил и версии аналитика; содержит структурированный вывод, поддержку, альтернативы и неизвестное. Исправление зависимости делает её устаревшей. Такая оценка не превращается в точное число без отдельного определения и проверки. Например, «до первой записанной атаки прошло X секунд» допустимо как приближение; «игрок безрассудно потерял X секунд» требует доказательств, которых это измерение не даёт.

## Пример прохождения чисел до профиля

Это **пример контракта по реальным данным**, не новый законченный портрет и не подтверждение устойчивой закономерности. Аудит сохраняет исходные ссылки и вычисленные примеры для четырёх матчей Jakiro на оценённой позиции 2:

| ID для раскрытия | Смерти по десятиминутным этапам L3 | L4: объединённое записанное время смерти / длительность | Записанный XP до 10:00 |
| --- | --- | --- | --- |
| 8959040566 | 2, 1, 0, 0 | 91 / 2261 с = 4,0% | 4744 |
| 8958839199 | 0, 2, 3, 1, 0 | 275 / 2744 с = 10,0% | 4673 |
| 8957325148 | 1, 3, 1, 1, 0 | 327 / 2450 с = 13,3% | 6654 |
| 8955721990 | 2, 4, 3, 1, 0, 1, 0 | 543 / 3748 с = 14,5% | 4056 |

L1 сохраняет смерть и `timeDead`; L2 строит интервал; L3 пересекает его с этапами; L4 хранит траекторию и числитель/знаменатель. L5 получает группу `hero=64, position=2, n=4`: медиана индивидуальных долей **11,68%**, диапазон **4,02–14,49%**; медиана записанного XP за первые десять минут **4708,5**. В группе три победы и одно поражение. Списка четырёх матчей в обычном пакете L6 уже нет: только агрегат и ключ раскрытия.

Аналитическое решение L6: «На Jakiro в центре у тебя пока заметен большой разброс времени, записанного в интервалах смерти. В части игр длительные отрезки проходят без смертей, поэтому считать частые смерти неизменной чертой твоего стиля рано. Рабочее направление — сравнить условия безопасных и дорогих этапов: состояние команды до них, долю ресурсов, опыт и действия после возвращения. Улучшение будем проверять в сопоставимых условиях, а не только по числу смертей». Это гипотеза для проверки, не вывод, что 11,68% времени можно было спасти.

Числа показывают вариативность; решение проверить условия — работа аналитика. Альтернатива: различия длительности, пиков и хода команды объясняют разброс. Связь с победой не установлена. Это пример того, как профиль обобщает данные и назначает следующую проверку, не пересказывает отдельные игры. Полезные сильные стороны и более точные рекомендации потребуют других семейств признаков; один этот пример не считается достаточным профилем.
