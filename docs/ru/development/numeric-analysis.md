# Числовые уровни L1–L4

[Разработка](README.md) · [Каталог и проект уровней](../architecture/cumulative-statistics.md) · [English](../../en/development/numeric-analysis.md)

Задача 5 реализована в `src/apps/analysis/numeric/`. Обычный матч проходит все четыре уровня без текста модели. Код сохраняет числовую траекторию с происхождением, качеством и контекстом героя, оценённой позиции, линии, обоих пиков и состояния команды. Существующие авторские разборы задачи 3 сохранены отдельно.

Это основа для будущей статистики дистанции, а не новый законченный профиль игрока. [Пространственные признаки и тепловые карты задачи 6 реализованы](spatial-analysis.md) в отдельном расширении L4 и группах L5. Сессии и межматчевые связи относятся к задаче 7, накопительные изменения и основной анализатор L5–L6 — к задачам 8–9. Исходные артефакты задачи 5 сохраняют прежние заглушки; пространственное расширение заменяет их в `enriched.json`.

## Что работает

| Уровень | Вход → вычисляемый результат |
| --- | --- |
| L1 | Проверенные локальные ответы → типизированные журналы целевого игрока; экономика, опыт, уровни и координаты всех участников; контекст и расхождения источников |
| L2 | Только L1 → непересекающиеся минутные окна; золото/XP по причинам; добивания; интервалы смерти и повторного включения; кластеры нанесения урона; покупки, применения, лечение, записанные варды/объекты |
| L3 | Только L2 → десятиминутные этапы: темпы и их изменения, доли времени, распределения минутных значений, сочетание фарма/урона, командные переходы и доля записанного командного XP |
| L4 | Только L3 → компактная траектория матча, итоговое участие, доли ресурсов, распределения длительностей, числовые признаки и ограничения |

Минутные окна покрывают `[0,duration]` по событиям и ровно `duration` секунд экспозиции. Промежуточные границы полуоткрытые; событие ровно на окончании матча попадает в последний интервал один раз. Предыгровые события сохраняются в L1; первые покупки учитывают предыгровое время. Более поздние этапы короткого матча отсутствуют, а не равны нулю.

Смерти и кластеры столкновений — дополнительные представления тех же данных. Золото/опыт/урон этапов складываются из непересекающихся окон, не из пересекающихся эпизодов. Поэтому две смерти с пересекающимися оценками отсутствия не удваивают время. Кластер считается один раз по времени начала; его урон остаётся распределённым по фактическому времени событий.

## Контракт и качество

Артефакты используют `numeric-analysis-1`, вычисления — `numeric-1`. `method_version=1` указывает версию паспорта каталога; `implementation_version` — версию реализации. В результате измерения есть ID, единицы, вид `source_observation` / `derived` / `proxy`, значение, числитель/знаменатель, качество, неопределённость и происхождение. Модельная оценка хранится отдельно и не заменяет измерение.

Состояния источника `missing`, `null`, `empty`, `malformed` различаются; нули и false не подменяют отсутствие. В числовых полях bool не принимается за число. Качество: `observed`, `partial`, `conflicting`, `unavailable`. `eligible` означает пригодность по выполненным проверкам данного измерения, **не доказанную полноту API**. Сохраняются число исходных/валидных записей, недопустимые записи, границы наблюдений и причины. Неизвестное временное покрытие равно null.

Расхождение журнала с итогом остаётся рядом с записанными значениями. Например, в семи матчах журнал ассистов непригоден для безусловных сравнений по времени, но итоговое участие `(kills + assists) / allied kills` независимо берётся из согласованных финальных значений. Не исключается весь матч. Для нулевого знаменателя доля равна null.

Свежесть снимка экономики/здоровья — максимум 5 секунд до запрошенного момента. Командная разность требует всех десяти участников, доля союзных ресурсов — всех пяти союзников. При пропуске возвращаются null и покрытие; переход через неизвестное состояние не додумывается. Соперник для личной разности — единственный враг с той же известной оценённой позицией. Совпадение позиции не означает доказанное прямое противостояние на линии.

## Определения, которые нельзя путать с оценками игры

- **XP и золото:** суммы записанных событий с родными причинами. Для золота причины разделены также по `isValidForStats`, включая неизвестное значение флага. Это не то же самое, что GPM/XPM × длительность, net worth или предполагаемый доход. Расхождение с итогом сохраняется, а не исправляется выдуманными событиями.
- **Уровни:** первое наблюдаемое достижение 6/12/18/25/30; недостигнутый уровень цензурирован окончанием матча. Проверяются монотонность и итоговый уровень.
- **Перерывы развития:** промежутки между положительными XP-событиями или добиваниями; крайние промежутки цензурированы. Это разрывы записей, не доказанная пассивность.
- **Наблюдаемая активность:** десятисекундные корзины с добиванием, уроном или уроном строению. Их длительности складываются как приближение; корзина с одним действием не доказывает десять секунд непрерывной полезной активности. Перемещения, обзор и другие действия в это определение не входят.
- **Время смерти:** объединение `[time,time+timeDead)` с обрезкой по матчу/этапу. Это приближение источника; buyback и погрешности могут менять фактическое отсутствие.
- **Возврат:** первое добивание/записанный урон/урон строению после расчётного конца смерти, до следующей смерти или конца матча. Нет события — правое цензурирование. Рядом сохраняются здоровье/мана перед смертью и перед первым действием, изменение имущества и командной разности. Нет оценки предотвратимости или потерянного потенциального золота.
- **Кластеры столкновений:** последовательности положительного урона целевого героя известным вражеским героям с промежутками до 15 секунд, при явных флагах отсутствия иллюзий с обеих сторон. Это кластеры нанесения урона, не полный детектор командных драк. Они пропускают участие без нанесения урона и действия собственных иллюзий. Полезность порога ещё требует проверки на дистанции.
- **Урон:** исходная сумма сохранена. Дополнительно разделены оригинальные вражеские цели, цели-иллюзии, неизвестная принадлежность и вклад собственных иллюзий по оригинальным целям. Последний — подмножество, его нельзя прибавлять второй раз. Даже очищенная сумма не всегда совпадает с финалом; причина остающихся расхождений не установлена.
- **Лечение:** отдельно собственное лечение, известные другие получатели и исходный итог `heroHealing`. Самолечение не считается поддержкой союзников. Спасённые жизни не вычисляются.
- **Покупки/применения:** родные ID и записанные времена/числа применений. Покупка не равна доставке или готовности предмета; отсутствие применения не доказывает упущенную возможность.
- **Варды/объекты/поддержка:** число записей по родным типам; счётчики `scanUsed`/`pingUsed` сохранены. Стэки из минутного массива, эффективный обзор и преобразование убийств в конкретные объекты остаются недоступными до проверки семантики. Родной `npcId` не выдаётся за проверенное название объекта.

Дополнительные поля внутри `details`, минутных окон и этапов — версия `numeric-1`: распределение внутренних разрывов, покрытие снимков, разделение урона, кластеры с порогом 15 с, корзины активности 10 с, пересечение наличия добивания и урона оригинальному герою в одной минуте. Эти определения дополняют паспорта задачи 4; они не вводят психологические оценки. На L4 остаются их ограниченные сводки, а полный список разрывов и эпизодов сохраняется ниже.

Это полный числовой артефакт матча, а не ограниченный пакет модели. Будущий L5 агрегирует такие записи кодом; тысяча L4 не передаётся аналитику списком.

Дополнительные различия, которые теперь видны:

1. **Итоговый XPM скрывает форму развития.** У четырёх Jakiro на позиции 2 XP к 10:00 составляет 4744, 4673, 6654 и 4056. Самый высокий итоговый XPM в этой группе — 1185 — относится к матчу с самым низким из этих стартовых значений. Поэтому итоговый XPM не годится как описание старта. Числовая траектория сохраняет оба наблюдения, а причина различий требует анализа условий.
2. **Сумма урона может измерять работу по иллюзиям.** У Juggernaut 206 425 записанного урона, но 173 720 приходится на цели-иллюзии. Остаётся 32 705 по оригинальным вражеским героям, включая 2299 от собственных иллюзий; это совпадает с финальным `heroDamage`. У других героев фильтрация не всегда устраняет расхождение, поэтому результат не объявлен универсально восстановленным итоговым уроном.
3. **Самолечение и поддержка различаются.** У Death Prophet записано 32 717 лечения себя при финальном `heroHealing=0`. Нельзя из нуля финального показателя заключать, что восстановления здоровья не было, или записывать самолечение в помощь союзникам.
4. **Возврат к событиям и цена смерти — разные вопросы.** У Underlord один возврат цензурирован, остальные имеют медиану 21 с; это не утверждение о медленной игре. Новый контракт сохраняет вид первого действия, состояние и границы применимости, чтобы аналитик мог выбрать подходящий эпизод.

Распределения по десяти играм пока являются таблицами прототипа. Устойчивые связи, причинность и портрет по этим отдельным числам не заявляются. Для этого нужны обобщения L5–L6 следующих задач.

## Выборочная интерпретация

Доступен отдельный обмен для **конкретной смерти**. На входе — числовой эпизод, соседние минутные окна, контекст и вопрос; до 16 000 UTF-8 байт включая оболочку. Ответ текущего Codex — до 8000 байт, 1–4 утверждения с видом, основаниями, альтернативой, неопределённостью и следующей проверкой. Внешнего API модели нет.

[Реальный сохранённый пример](../../../data/prototype/numeric-review-example.json): Death Prophet, матч 8960626424, смерть 41:33. Записано 90 с смерти, затем 14 с до добивания. Между контрольными точками имущество меняется на +53, командная разность — с +9146 до +9956. Следующая смерть — через 54 с после первого добивания. Вывод аналитика: полезно проверить решения при повторном включении; длительность первой смерти сама не доказывает потерю командного преимущества или ошибку.

Пакет и ответ хешируются; повторный запрос с теми же условиями получает тот же ключ. `read_numeric_review` возвращает сохранённый ответ после проверки зависимостей и исходных хешей. Изменение вопроса или числового узла требует новой оценки; изменение исходника делает старую недействительной. Проверяется структура и происхождение, не смысловая истинность текста.

## Сервисы и запуск

Основная операция: `src.apps.analysis.numeric.services.build_numeric_match_from_sources(root=..., match_id=..., account_id=...)`. Поддерживаются только ID из существующей десятиматчевой выборки `data/prototype/synthesis/selection.json`. Для текущего офлайн-сценария не нужны токены API и новые настройки.

Нижние операции доступны напрямую: `facts.build_numeric_facts(Sources)`, `episodes.build_numeric_episodes(l1)`, `phases.build_numeric_phases(l2)`, `phases.build_numeric_match(l3)`. Они проверяют версии и непосредственный нижний уровень. Сервисы выборочного анализа: `prepare_numeric_review`, `accept_numeric_review`, `read_numeric_review` экспортируются из `numeric.services`.

```powershell
# Один матч или вся существующая выборка
.venv\Scripts\python.exe -m src.apps.analysis.numeric.cli build --match-id 8960626424
.venv\Scripts\python.exe -m src.apps.analysis.numeric.cli build --all --summary .agent/tmp/numeric-run.json

# Независимая сверка на исходниках и повторный расчёт
.venv\Scripts\python.exe -m tools.check_numeric_analysis --output .agent/tmp/numeric-verification.json

# Формулы, границы, качество, версии, выборочный анализ и старые контракты
.venv\Scripts\python.exe -m unittest tools.test_numeric_analysis tools.test_analysis tools.test_analysis_series tools.test_synthesis
```

Для выборочного разбора подставьте путь `directory`, напечатанный `build`:

```powershell
.venv\Scripts\python.exe -m src.apps.analysis.numeric.cli prepare-review --directory <directory> --episode death:5 --question "Что нужно проверить в этом эпизоде?"
.venv\Scripts\python.exe -m src.apps.analysis.numeric.cli accept-review --directory <directory> --packet <packet.json> --response <response.json>
```

`<...>` — заменяемые аргументы. Шаблон структуры ответа есть в `response` сохранённого примера; нужно указать ID нового пакета и написать новый ответ. Копирование прежнего текста не является новым анализом.

Артефакты: `data/analysis/numeric/<match>/<key>/L1.json` … `L4.json`, плюс манифест с размерами, SHA и ревизиями. Ключ зависит от исходных ссылок, каталога, параметров, числового кода и используемых общих модулей. Чтение проверяет также цепочку детей. `data/analysis/` уже исключена из Git; в Git сохраняются только небольшие результаты проверки и пример. Старые артефакты не перезаписываются. Кеш матча — ещё не накопительное хранилище задачи 8.

## Что проверено

36 тестов проходят: 16 новых и 20 прежних. Проверены пересечения интервалов, конечная граница, нулевые/отсутствующие/невалидные данные, конфликт одного журнала, свежесть снимков, неизвестная позиция, цензурирование, принадлежность урона, неполный XP соперника, зависимости и повреждение артефактов, бюджет и повторное использование оценки.

Офлайн-проверка десяти матчей сверила исходные хеши/участников, 186 ссылок на выбранные записи, прямые суммы XP/золота, независимое объединение интервалов смерти, итоговое участие по OpenDota, сложение окон/этапов и граф уровней. Полный повторный расчёт дал те же ревизии; последующий запуск использовал кеш. Новых матчей — 0, обязательных ответов модели — 0. Эти проверки не доказывают полноту журналов, качество порога кластеризации или причинные связи.
