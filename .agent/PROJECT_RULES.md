# Правила проекта

Этот файл необходимо полностью перечитывать перед началом работы и после каждого сжатия, восстановления или потери контекста — до выполнения следующей задачи.

## Технологии и зависимости

- Использовать Python 3.14.7 и Pipenv. Версию Python фиксировать в `Pipfile`.
- Python-пакеты устанавливать в локальное окружение `.venv` в корне проекта. Для Pipenv задавать `PIPENV_VENV_IN_PROJECT=1`.
- Запускать Python-команды проекта через `.venv\Scripts\python.exe` или `py -3.14 -m pipenv run` с этим окружением.
- Добавлять зависимости только для конкретной задачи, требующей их использования.
- Всегда указывать точные версии всех явно объявляемых зависимостей проекта. Не использовать звёздочку (`*`), диапазоны или нефиксированные версии.
- Если выбранный менеджер пакетов поддерживает lock-файл, поддерживать его согласованность с манифестом зависимостей.
- Локальные окружения, кэши, секреты и результаты сборки не добавлять в Git.
- После выбора стека документировать требования и команды настройки в `docs/ru/environment/` и `docs/en/environment/`.

## Структура и документация

- Исходный код хранить в `src/`, вспомогательные инструменты — в `tools/`.
- Общую информацию и навигацию хранить в `README.md` и `README.en.md`.
- Документацию вести в `docs/ru/` и `docs/en/`, сохраняя соответствие разделов и актуальность обеих языковых версий.
- Описывать только фактически принятые решения и доступные команды. Не представлять планы как реализованные возможности.

## Архитектура кода: приложения и сервисы

### Приложения

- Организовывать функциональность в `src/apps/<app_name>/` по аналогии с приложениями Django: каждое приложение отвечает за отдельную область проекта и хранит относящиеся к ней код и структуры данных рядом.
- Границу приложения определять по его ответственности. Не создавать общее дерево из всех моделей, всех схем и всех сервисов разных областей.
- Внутри приложения использовать понятные модули по назначению: `services.py` — операции и сценарии; `schemas.py` — структуры входных и выходных данных и их валидация; `models.py` — модели хранения при появлении БД; `exceptions.py` — ошибки приложения; `enums.py` — перечисления.
- По необходимости добавлять `clients.py` для взаимодействия с внешними API, `dependencies.py` для подготовки зависимостей, `router.py` для HTTP-обработчиков и `cli.py` для команд. Создавать только модули, нужные текущей реализации, без пустого набора файлов для каждого приложения.
- Если модуль становится слишком большим, разбивать его на пакет с тем же назначением внутри приложения, сохраняя понятные точки импорта.

### Вызываемые сервисы

- Основную логику оформлять как явно вызываемые сервисные функции или методы в `services.py`. Одна операция должна иметь понятное назначение, входные параметры и результат.
- Для самостоятельной операции использовать функцию; связанные операции с общими зависимостями или состоянием можно объединять в класс сервиса. Не требовать класс, наследование или `__call__` для каждой операции.
- Указывать типы параметров и возвращаемых значений. Зависимости, нужные операции (клиент API, сессия БД, настройки, путь сохранения), передавать явно; для нескольких однотипных параметров предпочитать именованные аргументы.
- Сервисы должны быть доступны для прямого вызова из другого сервиса, CLI или будущего API. Не привязывать основную логику к HTTP-запросу, `Depends`, формированию HTTP-ответа или интерактивному вводу.
- Использовать `async def` для операций с асинхронными зависимостями. Обычные вычисления оставлять синхронными; длительный разбор реплея или блокирующий ввод-вывод не выполнять непосредственно в цикле асинхронных запросов.
- Ожидаемые ошибки обозначать явными исключениями приложения. Преобразовывать их в сообщение CLI или HTTP-ответ на границе вызова; не скрывать сбой под пустым успешным результатом.

### Точки входа и взаимодействие приложений

- Точка входа собирает зависимости и запускает сценарий. Обработчик CLI или HTTP принимает и проверяет ввод, вызывает сервис и представляет результат. Повторяемую последовательность шагов выносить в отдельный сервис сценария.
- Приложения взаимодействуют через явно названные сервисы и структуры данных. Не вызывать обработчики одного приложения из сервисов другого и не создавать циклические импорты.
- В `src/apps/common/` выносить только код, действительно общий для нескольких приложений. Логику конкретной области оставлять в её приложении.
- Настройки загружать через существующий `src/settings.py`; не читать TOML заново в каждом приложении. Сетевые запросы, сбор матчей и запуск парсера должны начинаться явным вызовом сервиса, а не при импорте модуля.

### Применение к получению данных

- Отделять взаимодействие с OpenDota, STRATZ и Steam/Game Coordinator, а также запуск парсера от сценария получения данных матча. Сценарий координирует эти операции через сервисы.
- Особенности протокола, авторизации, лимитов и ответов каждого внешнего источника держать в его клиенте или модуле интеграции, а не в CLI, точке входа или логике анализа.
- Отделять исходные ответы источников от приведённых к общему виду данных и вычисленных оценок. Сохранять происхождение и привязку к матчу при передаче данных между сервисами.
- Выбор архитектуры приложений и сервисов сам по себе не означает выбор Django, FastAPI, ORM или другого пакета. Добавлять конкретные технологии по требованиям текущей задачи и правилам зависимостей выше.

## Проверка изменений

- Проверять изменения способом, соответствующим задаче и выбранному стеку.
- Команды проверок и тестирования документировать в разделе `development` после их появления.
- При завершении сообщать, что проверено, и указывать ограничения проверки.

## Учёт задач

- Этот раздел описывает формат учёта, а не требование оформлять каждое поручение. Создавать файлы задач и записи в перечне или бэклоге только по явному запросу пользователя на оформление либо с его явного согласия согласно [правилам взаимодействия](INTERACTION_RULES.md).
- Хранить задачи в `.agent/tasks/`.
- Перечень задач вести в `.agent/tasks/INDEX.md`: для каждой задачи указывать номер, краткое описание, статус и ссылку на файл задачи.
- Бэклог вести отдельно в `.agent/tasks/BACKLOG.md`.
- Все оформленные задачи хранить в общей папке `.agent/tasks/items/`, без отдельных папок для каждой задачи.
- Markdown-файл задачи называть её номером: `.agent/tasks/items/1.md`, `.agent/tasks/items/2.md` и далее.
- Номера назначать последовательно, начиная с 1; использованные номера не переиспользовать и существующие задачи не перенумеровывать.
- В файле задачи указывать название, описание, ожидаемый результат, полный чек-лист декомпозированных подзадач и статус выполнения целиком. Порядок декомпозиции и обновления статусов определён в [правилах взаимодействия](INTERACTION_RULES.md). При завершении записывать результат и обновлять перечень задач.
- Файлы задач не смешивать с перечнем задач и бэклогом, которые находятся в корне `.agent/tasks/`.
- При оформлении задачи из бэклога создавать номерной Markdown-файл в `items/`, добавлять запись в перечень и заменять запись бэклога ссылкой на оформленную задачу либо удалять её из бэклога.

## Временные файлы агента

- Все временные файлы, которые агент создаёт для собственного удобства и эффективного выполнения поручения (черновики, промежуточные результаты, вспомогательные скрипты и логи), хранить в `.agent/tmp/`.
- Использование этой папки необязательно: агент сам решает, нужна ли она для текущего поручения, и может создавать в ней файлы без отдельного согласования в рамках этого поручения.
- Папка предназначена только для временных материалов агента. Итоговые файлы проекта хранить в соответствующих разделах проекта.
- `.agent/tmp/` исключена из Git. После клонирования создавать её при необходимости; не полагаться на сохранность её содержимого.
